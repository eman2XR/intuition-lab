# Intuition Lab — working instructions

Read `docs/HANDOFF.md` first, then `README.md`. Inspect `git status` before editing: ongoing work may be uncommitted. Do not discard local changes or delete run history to bypass daily budgets.

The product is a visual physics research lab, not the historical persona debate in `council.py`. Prioritize intuitive interactive visuals, actual browser captures, bounded revision, and honest scientific status. Keep the name **Intuition Lab** (renamed from The Council on 2026-10-29; the repository and site became `intuition-lab` on 2026-11-01, while the `council:` issue labels, browser storage keys, the launch agent `org.the-council.daily` and the `.council-state` folder keep the old names). Since 2026-11-13 there is no launch agent and no worker checkout (owner choice): daily work happens only while the owner's Claude Code session is open, through a session-only loop (`CronCreate`, not durable) that does one round by hand in this checkout. The session cannot run the lab's `claude` CLI agents (nested sandbox, exit 71), so the session does the research, engine, guide and checks itself and runs the reviews as subagents; it is bounded to at most one new guide a day and three review rounds. The owner approved publishing those guides once they pass the hand-made checks below; each ends with `python3 -m lab push announce <id>` and `python3 -m lab checkin "<line>"`. `.council-state` (ledger, notification keys and subscriptions) lives in this checkout.

The coordinator owns writes, validation, scheduling and publication. Models return structured data. The one explicit, gated exception: on an idle publishing morning the daily run may BUILD a new picture engine from a research brief (`lab/build_engine.py`), or REVISE a published guide from owner feedback (`lab/revise.py`), where the model returns engine code as a bounded structured object that the coordinator splices into the site (at fixed `AGENT-ENGINES` markers for a new engine, or in place of the named kind's draw function, map entry and Physics methods for a revision) and keeps only if every gate passes. Owner decision (2026-11-13): a built engine whose first guide passes every gate, every render check and all four reviews is committed to `main` with that guide and published without waiting for the owner (`_publish_build`; a failed push undoes the commit and rolls everything back byte-for-byte). A build whose guide falls short of that commits the five engine files and the draft onto a dedicated `engine-candidate/<day>-<kind>` branch instead, and a successful revision commits the revised engine files and the revised `web/published/<id>/record.json` (updated scene, re-rendered frames, a feedback-revision provenance note) onto a `feedback-revision/<day>-<id>` branch; each pushes only its own branch (never `main`, never `--force`), then restores the worker's `main` working tree to its exact original bytes, so the code exists only on the review branch. The owner is told through a proposal (kind `engine` or `revision`) and the dashboard that a picture is ready to review; it goes live only when a human merges the branch into `main` (`python3 -m lab approve-engine <branch>`, or `approve_engine`, re-runs the gates, prints the engine and record diff, and fast-forwards). Any gate failure, or any failure at all, restores every touched file to its exact original bytes, leaves no draft or branch on `main`, and (for a build) falls back to `research_brief` then `blueprint`, or (for a revision) comments that the feedback needs a hand revision and leaves the issue open. Because reviewed builds go live without a human reading the code, the engine validators also refuse, before any edit, code that touches the page, browser, network or timers (`browser_free`: no window/document/location/navigator/fetch/timers and the like, no `this` outside the physics object, no string-key property access), map-entry values that run at load (`entry_values_only`), and labels or categories that are not plain words; template `${...}` expressions are scanned as code; label, category and notes are spliced as JSON string literals, and `lab/topics.py` must still compile. The site's Content-Security-Policy (in `web/index.html`) lets the page load only its own files and connect only to itself and the GitHub API. Keep all of these; the sandbox remains the behavioural gate. Support both Claude Code and Codex using their existing authentication; direct OpenAI API is optional. Preserve organization-managed CLI settings. Never bypass tool permissions or extract credentials.

Tests: `python3 -m unittest discover -s tests -v`. Renderer check: `python3 -m lab run --provider fixture --topic gravity-clocks --rounds 2`. Live calls consume usage; inspect existing run records before starting another. Read the handoff's current-state section for unfinished verification.

Only accepted live investigations, or hand-made guides the owner explicitly asks to publish, may enter `web/published/`. A hand-made guide must pass the render checks, its model checks and a final accuracy, visual and beginner review, and its record must say in `provenance.intro_note` that it was made in a coding session. Agent-built engines and feedback revisions (the gated exception above) must pass the build gates before their draft or revised record is saved and their candidate branch is pushed: `node --check` on `scene.js`/`physics.js`/`app.js`; `allChecks()` with zero failures plus at least three non-vacuous checks for the model that call its model functions; a function-only structural rule on the `scene` field (only function and named `const`/`let` declarations, nothing that runs at load — no IIFEs or bare calls) and a method-and-literal-only rule on the `physics` field; a locked-down SANDBOX render (`lab.render.gate_probe`) that blocks all network and overrides timers, workers, sockets, beacons and `document.cookie` to throw, so any side-effecting code fails behaviourally rather than by pattern matching; and a full `lab.render.capture` render (a placeholder scene for a build, the revised scene for a revision) with every render check passing. A revision's in-place splice is fragile (it locates the kind's draw function, map entry and Physics methods by name); if a target cannot be located or the result is invalid, the gates reject it and everything rolls back byte-for-byte. The draft's or revision's `provenance.intro_note` must say the engine or revision was built by the agents and awaits the owner's review. Apart from a fully reviewed build (above), agent-written engine code and revised guides are NEVER pushed to `main` or the live site; a human merges the review branch to make it live. Guides the session loop builds by hand are owner-approved for publishing once they pass the hand-made checks above, including the four subagent reviews. Never promote fixtures, failed scientific reviews, or drafts the owner has not approved. Never force-push. The daily scheduler must retain its per-day cap and lock (the feedback revision and the engine build share one once-a-day idle slot, which `research_brief`/`blueprint` fall back to), and must not execute an unbounded agent loop.
