# Intuition Lab — working instructions

Read `docs/HANDOFF.md` first, then `README.md`. Inspect `git status` before editing: ongoing work may be uncommitted. Do not discard local changes or delete run history to bypass daily budgets.

The product is a visual physics research lab, not the historical persona debate in `council.py`. Prioritize intuitive interactive visuals, actual browser captures, bounded revision, and honest scientific status. Keep the name **Intuition Lab** (renamed from The Council on 2026-10-29; the repository and site became `intuition-lab` on 2026-11-01, while the `council:` issue labels, browser storage keys, the launch agent `org.the-council.daily` and the worker folder keep the old names).

The coordinator owns writes, validation, scheduling and publication. Models return structured data. The one explicit, gated exception: on an idle publishing morning the daily run may BUILD a new picture engine from a research brief (`lab/build_engine.py`), or REVISE a published guide from owner feedback (`lab/revise.py`), where the model returns engine code as a bounded structured object that the coordinator splices into the site (at fixed `AGENT-ENGINES` markers for a new engine, or in place of the named kind's draw function, map entry and Physics methods for a revision) and keeps only if every gate passes. NO agent-written engine CODE, and no change to a live guide, ever reaches `main` or the live site: a successful build commits the five engine files and the draft onto a dedicated `engine-candidate/<day>-<kind>` branch, and a successful revision commits the revised engine files and the revised `web/published/<id>/record.json` (updated scene, re-rendered frames, a feedback-revision provenance note) onto a `feedback-revision/<day>-<id>` branch; each pushes only its own branch (never `main`, never `--force`), then restores the worker's `main` working tree to its exact original bytes, so the code exists only on the review branch. The owner is told through a proposal (kind `engine` or `revision`) and the dashboard that a picture is ready to review; it goes live only when a human merges the branch into `main` (`python3 -m lab approve-engine <branch>`, or `approve_engine`, re-runs the gates, prints the engine and record diff, and fast-forwards). Any gate failure, or any failure at all, restores every touched file to its exact original bytes, leaves no draft or branch on `main`, and (for a build) falls back to `research_brief` then `blueprint`, or (for a revision) comments that the feedback needs a hand revision and leaves the issue open. Agent-built engines and their first guide always land as owner-review DRAFTS on the candidate branch, never auto-published and never on the live site. Support both Claude Code and Codex using their existing authentication; direct OpenAI API is optional. Preserve organization-managed CLI settings. Never bypass tool permissions or extract credentials.

Tests: `python3 -m unittest discover -s tests -v`. Renderer check: `python3 -m lab run --provider fixture --topic gravity-clocks --rounds 2`. Live calls consume usage; inspect existing run records before starting another. Read the handoff's current-state section for unfinished verification.

Only accepted live investigations, or hand-made guides the owner explicitly asks to publish, may enter `web/published/`. A hand-made guide must pass the render checks, its model checks and a final accuracy, visual and beginner review, and its record must say in `provenance.intro_note` that it was made in a coding session. Agent-built engines and feedback revisions (the gated exception above) must pass the build gates before their draft or revised record is saved and their candidate branch is pushed: `node --check` on `scene.js`/`physics.js`/`app.js`; `allChecks()` with zero failures plus at least three non-vacuous checks for the model that call its model functions; a function-only structural rule on the `scene` field (only function and named `const`/`let` declarations, nothing that runs at load — no IIFEs or bare calls) and a method-and-literal-only rule on the `physics` field; a locked-down SANDBOX render (`lab.render.gate_probe`) that blocks all network and overrides timers, workers, sockets, beacons and `document.cookie` to throw, so any side-effecting code fails behaviourally rather than by pattern matching; and a full `lab.render.capture` render (a placeholder scene for a build, the revised scene for a revision) with every render check passing. A revision's in-place splice is fragile (it locates the kind's draw function, map entry and Physics methods by name); if a target cannot be located or the result is invalid, the gates reject it and everything rolls back byte-for-byte. The draft's or revision's `provenance.intro_note` must say the engine or revision was built by the agents and awaits the owner's review. Agent-written engine code and revised guides are NEVER pushed to `main` or the live site; a human merges the review branch to make it live. Never promote fixtures, failed scientific reviews, or drafts the owner has not approved. Never force-push. The daily scheduler must retain its per-day cap and lock (the feedback revision and the engine build share one once-a-day idle slot, which `research_brief`/`blueprint` fall back to), and must not execute an unbounded agent loop.
